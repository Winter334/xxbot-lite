# 12-战斗系统 V2 事件效果设计

> 状态：Draft v2
> 创建日期：2026-07-25
> 作用：为下一代战斗系统定义事件、效果、状态、伤害、战报与内容重做口径。
>
> 注意：本文是 **Combat V2 设计稿**，不代表当前线上实现口径。当前有效规则仍以 `specs/00-当前实现口径.md` 与现有代码为准。

---

## 1. 设计背景

当前战斗系统已经从最早的“三维 + 普攻 + 简单胜负”自然生长为效果密集型系统：法宝词条、器灵神通、灼烧、咒印、护盾、净化、反伤、复活、处决、追伤、韧性等机制都挤在同一个 `combat_service.py` 中。

这导致几个明显问题：

1. **新效果开发不友好**
   - 新增词条往往要同时修改数据定义、触发分支、状态字段、伤害处理、日志文本。
   - 效果逻辑散落在多个 hook 中，很难一眼看出完整行为。

2. **互动顺序不透明**
   - 护盾、减伤、韧性、真伤、反伤、复活、处决等节点的先后顺序依赖函数调用位置。
   - 加一个新机制时，很容易无意改变旧机制结果。

3. **状态语义过度复用字段**
   - 例如灼烧、灵势、裂铠、春生追击、死兆等都借同一个 `_StatusEffect` 承载，但各自解释字段的方式不同。
   - 状态是“字符串 + 一堆可选字段”，缺乏明确标签、叠层策略、来源规则。

4. **伤害管线不统一**
   - 普攻、DOT、追伤、反伤、引爆、固定伤害各自走不同 helper。
   - 某笔伤害是否吃增伤、减伤、护盾、韧性，经常取决于实现时用了哪个函数。

5. **战报与机制耦合**
   - 玩家可见中文文本写在机制分支里。
   - 后续想做更好的战报、调试信息或动画时，很难复用结构化结果。

Combat V2 的目标不是“把旧代码拆成多个文件”，而是重新定义一套更清晰的底层模型。设计上参考《杀戮尖塔》的思想：

> 战斗由事件推进；效果监听事件并产生动作；动作修改状态并产生日志。

---

## 2. V2 设计目标

### 2.1 核心目标

1. **新效果好写**
   - 常见效果应能通过声明式模板完成。
   - 复杂神通允许写脚本处理器，但必须挂在明确事件上。

2. **互动清晰**
   - 所有关键结算节点都有明确生命周期与优先级。
   - 护盾、减伤、韧性、复活、处决等高风险机制不靠隐式调用顺序。

3. **战报好看**
   - 内部先产生结构化 `LogEvent`。
   - 展示层再把结构化事件翻译成玩家可读中文。
   - 同一场战斗可以输出简略战报、完整战报、调试战报。

4. **数值可控**
   - 明确乘区、加区、上限、触发频率与场景修正。
   - 防止法宝多槽 + 器灵 + 状态叠层后出现不可控爆炸。

5. **可测试**
   - 随机数由战斗上下文统一提供。
   - 事件、动作、伤害包、日志都可被单测断言。

### 2.2 非目标

Combat V2 不追求：

- 职业 / 门派 / 阵容克制大系统。
- 多单位编队或召唤物体系。
- 玩家实时操作或手动选技能。
- 完整复刻现有 47 个法宝词条和 25 个器灵神通。
- 为未来不确定玩法预埋复杂架构。

V2 的目标是让一期修仙 Bot 的自动战斗更容易扩展，而不是把项目升级成大型战斗引擎。

## 3. 设计总原则

### 3.1 战斗是确定性状态机

在给定以下输入时，一场战斗结果应可复现：

- 双方战斗快照。
- 场景标签。
- 效果定义版本。
- RNG 种子 / 随机序列。

所有随机判定都必须从 `BattleContext.rng` 获取，不允许效果自己创建随机源。

### 3.2 机制与展示分离

效果处理器不直接拼最终战报文本。它只产生结构化事件，例如：

```text
PowerTriggered(source=聚灵, owner=青玄)
StatusStackChanged(status=灵势, stacks_before=2, stacks_after=3)
DamageApplied(kind=burn, amount=1200, target_hp_after=8800)
```

展示层根据事件模板输出中文：

```text
青玄的「聚灵」牵引灵机，凝成第 3 层「灵势」。
赤霄身上的 3 层「灼烧」侵蚀，承受 1200 点焚伤。
```

### 3.3 普通效果声明式，特殊效果脚本式

大多数词条应使用通用模板：

- 上状态。
- 加护盾。
- 治疗。
- 造成伤害。
- 清除状态。
- 偷取 / 转移状态。
- 修改某个数值阶段。

少数复杂效果可写专用处理器，例如：

- 绝命：标记、转化、处决。
- 雷罚：充能、阈值、天劫结算。
- 万咒：咒印爆发并生成随机负面状态。
- 涅槃：死亡拦截、复活、复活后强化。

### 3.4 所有伤害都是 DamagePacket

不再允许“某效果直接扣目标 HP”作为常规实现。所有伤害都构造成 `DamagePacket`，由统一伤害管线处理。

例外只允许极少数机制性结果，例如：

- 战斗规则直接判负。
- 机制性处决，且必须显式标记 `kind=execute`。

### 3.5 内容可以重做

V2 不要求旧效果 1:1 迁移。现有法宝词条和器灵神通作为素材库处理：

- 有趣机制保留。
- 重复效果合并。
- 难解释、难平衡、强耦合的效果重做或删除。
- 器灵继续保持“大颗粒、改规则”的定位。
- 法宝词条偏“多槽位、小颗粒、可构筑”。

## 4. 核心抽象

### 4.1 BattleContext

一场战斗的运行上下文。

建议职责：

- 保存双方 `CombatantState`。
- 保存场景标签。
- 保存 RNG。
- 保存当前回合、行动序号、事件队列。
- 提供统一 API：派发事件、执行动作、记录日志、查询状态。

示意结构：

```python
@dataclass(slots=True)
class BattleContext:
    combatants: tuple[CombatantState, CombatantState]
    scene_tags: frozenset[str]
    rng: RandomLike
    round_no: int = 0
    action_index: int = 0
    event_queue: deque[BattleEvent] = field(default_factory=deque)
    logs: list[LogEvent] = field(default_factory=list)
```

### 4.2 CombatantState

战斗中的单位状态，不直接等同于角色数据库模型。

建议字段：

- `id`：战斗内稳定 ID，例如 `challenger` / `defender`。
- `name`：展示名。
- `base_stats`：基础杀伐、护体、身法、最大生命。
- `hp`：当前生命。
- `block` / `shield`：临时护盾池，或用状态承载。
- `powers`：由法宝、器灵、命格、场景提供的常驻能力。
- `statuses`：运行中状态。
- `flags`：本场战斗临时标记，如是否已复活。
- `counters`：充能、回合计数等。

### 4.3 EffectSource

效果来源，用来回答“这个效果从哪里来”。

来源类型包括：

| source_type | 说明 |
|---|---|
| `artifact_affix` | 法宝词条 |
| `spirit_power` | 器灵神通 |
| `fate` | 命格 |
| `title` | 称号 |
| `realm` | 境界基础规则 |
| `scene` | 场景规则 |
| `temporary` | 证道战场临时祝福 / 临时敌人词条 |
| `status` | 状态自身派生出的持续效果 |

同一个效果 ID 可以有多个实例，例如重复法宝词条。实例必须保留独立 `source_instance_id`，避免错误去重。

### 4.4 Power

`Power` 表示常驻能力，接近《杀戮尖塔》的 Power。它一般来自法宝词条、器灵神通、命格或场景。

特点：

- 挂在某个单位身上。
- 监听事件。
- 可以修改事件，也可以产生动作。
- 通常不可被净化，不作为战斗状态显示，除非需要展示。

例子：

- 法宝词条「聚灵」：监听 `RoundStart`，给自己上「灵势」。
- 器灵神通「涅槃」：监听 `BeforeDeath`，拦截死亡并复活。
- 场景规则「通天塔 BOSS」：战斗开始给敌人附加额外威压。

### 4.5 Status

`Status` 表示战斗中可变化、可显示、可叠层、可移除的状态。

特点：

- 挂在某个单位身上。
- 有层数、持续时间、标签、来源。
- 可以监听事件。
- 可以被净化 / 偷取 / 转移 / 驱散，取决于规则。

例子：

- 「灵势」：正面，叠层，提升杀伐与伤害。
- 「灼烧」：负面，叠层，回合结束造成 DOT。
- 「咒印」：负面标记，可被绝命等机制消耗。
- 「裂铠」：正面护盾状态，破裂时反伤。
- 「死兆」：负面特殊标记，不可净化，可能触发处决。

### 4.6 BattleEvent

`BattleEvent` 是战斗推进的事实或询问。

事件分两类：

1. **通知型事件**
   - 例如 `RoundStart`、`StatusApplied`、`DamageApplied`。
   - 效果可以响应并产生动作。

2. **可修改型事件**
   - 例如 `HitCheck`、`CritCheck`、`DamageModify`、`BeforeDeath`。
   - 效果可以修改事件结果。

事件必须包含：

- `event_type`
- `round_no`
- `actor`
- `target`
- `source`
- `payload`
- `cancelled / resolved` 等控制字段，视事件类型决定。

### 4.7 Action

`Action` 是对战斗状态的修改请求。

常见动作：

| Action | 说明 |
|---|---|
| `AttackAction` | 发起一次普通攻击流程 |
| `DealDamageAction` | 造成一笔伤害 |
| `HealAction` | 治疗 |
| `ApplyStatusAction` | 添加状态 |
| `RemoveStatusAction` | 移除状态 |
| `ModifyStatusStacksAction` | 修改状态层数 |
| `GainShieldAction` | 获得护盾 |
| `CleanseAction` | 净化负面状态 |
| `DispelAction` | 驱散正面状态 |
| `ReviveAction` | 复活 |
| `ExecuteAction` | 机制性处决 |
| `AddCounterAction` | 增加充能或计数 |

效果处理器不直接改 HP / 状态列表，而是提交 Action。Action 由战斗上下文统一执行。

### 4.8 DamagePacket

`DamagePacket` 是统一伤害描述。

建议字段：

```python
@dataclass(slots=True)
class DamagePacket:
    source: EffectSource
    actor_id: str
    target_id: str
    base_amount: int
    kind: DamageKind
    tags: frozenset[str]
    can_crit: bool = False
    is_critical: bool = False
    can_be_buffed: bool = True
    can_be_vulned: bool = True
    can_be_reduced: bool = True
    can_be_pierced: bool = True
    can_be_shielded: bool = True
    respects_resilience: bool = True
    triggers_on_hit: bool = False
    triggers_on_be_hit: bool = True
    can_lifesteal: bool = False
    can_kill: bool = True
```

### 4.9 LogEvent

`LogEvent` 是结构化战报事件，不等同于最终文本。

建议字段：

- `log_type`
- `round_no`
- `actor_id`
- `target_id`
- `source`
- `amount`
- `status_id`
- `stacks_before / stacks_after`
- `hp_before / hp_after`
- `tags`
- `importance`
- `template_key`

展示层根据 `template_key` 和 payload 生成中文文本。

## 5. 战斗生命周期

V2 推荐采用固定生命周期。每个阶段派发对应事件，效果只能在声明的阶段介入。

### 5.1 初始化阶段

1. 从角色 / 敌人快照构造 `CombatantState`。
2. 根据法宝、器灵、命格、场景创建 `Power`。
3. 初始化 HP、基础属性、场景标签。
4. 派发 `BattleSetup`。
5. 派发 `BattleStart`。

### 5.2 回合循环

一场战斗最多仍建议保留回合上限。V2 初始建议沿用当前 20 回合口径，除非后续数值重做需要调整。

每回合流程：

1. `RoundStart`
2. 回合开始状态处理
3. 决定本回合行动顺序
4. 先手单位行动
5. 后手单位行动
6. `RoundEnd`
7. 回合结束状态处理
8. 状态持续时间衰减
9. 胜负检查

### 5.3 行动流程

一次普通攻击建议拆为：

1. `BeforeAction`
   - 控制、封禁、跳过行动在这里处理。
2. `ActionDeclared`
   - 宣告本次行动类型。
3. `BeforeAttack`
   - 攻击前加成、额外攻击、蓄力等。
4. `HitCheck`
   - 命中 / 闪避判定。
   - 效果可强制命中、强制闪避或修改命中率。
5. `CritCheck`
   - 暴击判定。
   - 效果可强制暴击或修改暴击率 / 暴击伤害。
6. `BuildDamagePacket`
   - 构造基础普攻伤害包。
7. `DamageModify`
   - 攻方增伤、守方承伤、减伤、穿透、场景修正等。
8. `BeforeDamageApplied`
   - 护盾前或受伤前机制，例如玄甲类预减伤。
9. `DamageApplied`
   - 实际扣血。
10. `AfterDamageApplied`
    - 吸血、受击触发、反击触发。
11. `AfterHit`
    - 命中后上状态、追伤、充能。
12. `AfterCrit`
    - 暴击后触发。
13. `DeathCheck`
    - 死亡检查、复活、处决。
14. `ActionFinished`

### 5.4 行动顺序

V2 推荐 **每回合重新计算行动顺序**：

1. `RoundStart` 效果先结算。
2. 根据当前身法、先攻修正、控制状态决定顺序。
3. 同速随机。

原因：

- 身法 buff / debuff 对战斗节奏更直观。
- “先机”“减速”“破步”等效果更容易解释。
- 后续若要实现“下回合先手”也有明确位置。

如果需要降低变化频率，也可以在内容层限制身法效果持续时间和数值。

## 6. 事件系统与优先级

### 6.1 基本派发规则

当某个事件发生时，战斗上下文按以下顺序收集监听器：

1. 场景规则。
2. 事件 actor 的 Power。
3. 事件 actor 的 Status。
4. 事件 target 的 Power。
5. 事件 target 的 Status。
6. 全局规则。

同一组内按 `priority` 从小到大执行；相同优先级按来源实例创建顺序执行。

建议优先级分段：

| priority 范围 | 用途 |
|---|---|
| `-1000 ~ -501` | 系统规则、场景硬规则 |
| `-500 ~ -101` | 强制改写，例如强制命中、死亡拦截 |
| `-100 ~ -1` | 前置修正，例如先攻、预减伤 |
| `0` | 普通效果默认值 |
| `1 ~ 100` | 后置触发，例如命中后追加状态 |
| `101 ~ 500` | 清理、转化、连锁效果 |
| `501 ~ 1000` | 调试、战报补充、兜底规则 |

### 6.2 事件队列

效果响应事件时不要递归直接处理新事件，而是提交 Action 或追加事件到队列。

推荐规则：

- 主流程事件按固定生命周期产生。
- Action 执行时可以产生派生事件。
- 派生事件进入队列，按 FIFO 处理。
- 每个事件记录父事件 ID，方便调试战报。
- 必须设置单场事件数上限，防止无限循环。

### 6.3 连锁限制

为了数值和性能可控，V2 需要限制连锁：

- 追伤默认不再触发新的“命中后”效果，除非 `triggers_on_hit=True`。
- DOT 默认不触发“命中后”效果。
- 反伤默认不触发反伤，避免反伤互弹。
- 净化触发的追伤 / 治疗默认不再触发新的净化链。
- 同一来源同一事件默认每次只触发一次，除非明示可重复。

## 7. 统一伤害模型

### 7.1 DamageKind

建议伤害类型：

| kind | 说明 |
|---|---|
| `attack` | 普通攻击伤害 |
| `critical_attack` | 暴击普攻，可作为 attack 的标记而非独立类型 |
| `dot` | 持续伤害，如灼烧 |
| `bonus` | 固定追伤 / 额外伤害 |
| `counter` | 反击伤害 |
| `reflect` | 反伤 |
| `burst` | 引爆类伤害 |
| `spirit` | 器灵神通直接伤害 |
| `execute` | 处决 / 斩杀 |
| `true` | 真伤，谨慎使用 |

### 7.2 默认伤害矩阵

| 伤害类型 | 吃增伤 | 吃承伤 | 吃减伤 | 吃穿透 | 吃护盾 | 吃韧性 | 可暴击 | 触发命中后 | 可吸血 | 可击杀 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 普攻 | 是 | 是 | 是 | 是 | 是 | 是 | 是 | 是 | 是 | 是 |
| DOT / 灼烧 | 是 | 是 | 否 | 否 | 否 | 是 | 否 | 否 | 特例 | 是 |
| 固定追伤 | 否 | 是 | 是 | 是 | 是 | 是 | 否 | 否 | 否 | 是 |
| 引爆 | 否 | 是 | 是 | 是 | 是 | 是 | 否 | 否 | 否 | 是 |
| 反击 | 是 | 是 | 是 | 是 | 是 | 是 | 可选 | 否 | 可选 | 是 |
| 反伤 | 否 | 是 | 否 | 否 | 否 | 是 | 否 | 否 | 否 | 是 |
| 处决 | 否 | 否 | 否 | 否 | 否 | 否 | 否 | 否 | 否 | 是 |
| 真伤 | 否 | 否 | 否 | 否 | 可选 | 否 | 否 | 否 | 否 | 是 |

说明：

- `execute` 是规则结果，不是常规数值伤害，应极少使用。
- `true` 真伤必须明确原因，默认不进入普通词条池。
- DOT 是否可吸血由来源决定，例如某个器灵可以声明“从灼烧伤害中吸血”。

### 7.3 伤害结算阶段

一笔伤害建议按固定阶段处理：

1. `BaseAmount`
   - 计算基础值，例如杀伐、最大生命、层数。
2. `AttackModifier`
   - 攻方造成伤害提高 / 降低。
3. `TargetVulnerability`
   - 守方承伤提高 / 降低。
4. `ReductionAndPierce`
   - 守方减伤与攻方穿透合并处理。
5. `SceneModifier`
   - PvP / PvE / BOSS / 证道等场景修正。
6. `PreShieldMitigation`
   - 受击前特殊防御，例如玄甲类。
7. `Shield`
   - 护盾抵扣。
8. `Resilience`
   - 境界基础韧性。
9. `ApplyHpLoss`
   - 实际扣血。
10. `PostDamage`
    - 吸血、反击、低血触发、死亡检查。

### 7.4 乘区控制

V2 建议将伤害相关数值分为少数固定乘区：

1. **基础属性区**：杀伐 / 护体 / 身法。
2. **攻方增伤区**：造成伤害提高。
3. **守方承伤区**：受到伤害提高。
4. **守方减伤区**：受到伤害降低。
5. **暴击区**：暴击倍率。
6. **场景区**：PvP / BOSS / 证道修正。
7. **最终区**：极少数全局最终修正。

原则：

- 普通法宝词条尽量只进入 1 个乘区。
- 器灵神通可以改变规则，但要给出触发频率或上限。
- 同名状态叠层必须有上限。
- 多件重复词条允许存在，但总效果要受全局上限约束。

## 8. 状态与叠层模型

### 8.1 StatusDefinition

每个状态需要独立定义，不再只靠中文名判断。

建议字段：

```python
@dataclass(frozen=True, slots=True)
class StatusDefinition:
    status_id: str
    name: str
    polarity: StatusPolarity  # positive / negative / neutral
    tags: frozenset[str]
    default_duration: DurationSpec
    stacking: StackingPolicy
    cleanseable: bool = True
    stealable: bool = False
    transferable: bool = False
    dispellable: bool = True
    visible: bool = True
```

### 8.2 StatusInstance

运行时状态实例：

```python
@dataclass(slots=True)
class StatusInstance:
    definition: StatusDefinition
    owner_id: str
    source: EffectSource
    stacks: int = 1
    duration: int | None = None
    magnitude: dict[str, int | float] = field(default_factory=dict)
    metadata: dict[str, object] = field(default_factory=dict)
```

### 8.3 状态标签

建议标签：

| tag | 说明 |
|---|---|
| `buff` | 正面强化 |
| `debuff` | 负面弱化 |
| `dot` | 持续伤害 |
| `burn` | 灼烧系 |
| `curse` | 咒系 |
| `mark` | 标记 |
| `control` | 控制 |
| `shield` | 护盾 |
| `stat_modifier` | 属性修改 |
| `damage_modifier` | 伤害修改 |
| `heal_modifier` | 治疗修改 |
| `special` | 特殊规则 |

标签用于效果筛选，例如：

- 净化：移除 `polarity=negative` 且 `cleanseable=True`。
- 偷取：选择 `stealable=True` 的正面状态。
- 灼烧增伤：检查目标是否拥有 `tag=burn`。
- 绝命：检查 `tag=curse` 或 `status_id=curse_seal`。

### 8.4 叠层策略

建议支持以下策略：

| 策略 | 说明 | 示例 |
|---|---|---|
| `add_stack_cap` | 增加层数，到上限停止 | 灵势、灼烧、咒印 |
| `refresh_duration` | 层数不变，刷新持续时间 | 短时减伤 |
| `extend_duration` | 延长持续时间 | 持续增益 |
| `replace_if_stronger` | 新数值更强才替换 | 护盾类、强弱 buff |
| `independent` | 每次都是独立实例 | 多件裂铠、独立反伤 |
| `consume_one` | 触发时消耗一层 | 疾锋被命中减弱 |
| `consume_all` | 触发时消耗全部层数 | 引爆、处决蓄力 |
| `convert_at_cap` | 满层转化为另一状态 | 咒印转死兆 |

### 8.5 持续时间口径

状态持续时间必须明确在哪个阶段衰减。

建议统一：

- 默认状态在所属者的 `RoundEnd` 后衰减。
- DOT 在 `RoundEnd` 先结算，再衰减。
- “下次攻击”类状态用 `charges` 或 `remaining_uses`，不要伪装成持续回合。
- 永久到战斗结束的状态 `duration=None`。

## 9. 效果编写方式

### 9.1 EffectDefinition

法宝词条、器灵神通、命格等都可以转化为 `EffectDefinition`。

建议字段：

```python
@dataclass(frozen=True, slots=True)
class EffectDefinition:
    effect_id: str
    name: str
    source_type: str
    rarity_or_tier: str | None
    triggers: tuple[TriggerDefinition, ...]
    rolls: RollSpec
    description_template: str
    tags: frozenset[str]
```

### 9.2 TriggerDefinition

普通效果用 trigger + condition + action 描述。

```python
@dataclass(frozen=True, slots=True)
class TriggerDefinition:
    event_type: str
    priority: int
    conditions: tuple[ConditionSpec, ...]
    actions: tuple[ActionSpec, ...]
    once_per: OncePerSpec | None = None
```

例子：

```yaml
effect_id: artifact_juling
name: 聚灵
triggers:
  - event: round_start
    conditions:
      - owner_is_event_actor
    actions:
      - apply_status:
          target: owner
          status_id: ling_shi
          stacks: 1
```

### 9.3 ConditionSpec

常见条件模板：

- `owner_is_actor`
- `owner_is_target`
- `target_has_status(tag=burn)`
- `owner_hp_below(percent=50)`
- `round_no_at_least(n)`
- `first_time_per_battle`
- `scene_has(tag)`
- `damage_kind_is(kind)`
- `event_is_critical`
- `rng_chance(percent)`

### 9.4 ActionSpec

常见动作模板：

- `apply_status`
- `remove_status`
- `cleanse`
- `dispel`
- `deal_damage`
- `heal`
- `gain_shield`
- `modify_event_value`
- `force_hit`
- `force_crit`
- `add_counter`
- `consume_counter`
- `convert_status`
- `log`

### 9.5 脚本处理器

复杂效果使用脚本处理器，但必须遵守：

1. 只能通过 BattleContext API 修改状态。
2. 必须声明监听事件和优先级。
3. 必须声明是否可重复触发。
4. 必须为关键结果产生结构化日志。
5. 必须有单测覆盖。

示意：

```python
class NiepanHandler(EffectHandler):
    listens_to = (EventType.BEFORE_DEATH,)
    priority = -400

    def handle(self, ctx: BattleContext, event: BeforeDeathEvent) -> None:
        ...
```

## 10. 样例效果设计

### 10.1 聚灵 / 灵势

定位：稳定成长型构筑核心。

- `聚灵` 是 Power，来源于法宝词条。
- `灵势` 是 Status，正面，最多 10 层。

规则：

```yaml
artifact_juling:
  trigger: round_start
  action: apply_status(owner, ling_shi, +1 stack)

status_ling_shi:
  max_stacks: 10
  modifiers:
    - phase: current_atk
      op: add_percent
      value: atk_pct_per_stack * stacks
    - phase: damage_dealt
      op: add_percent
      value: damage_pct_per_stack * stacks
```

设计重点：

- 叠层上限清楚。
- 攻击属性与造成伤害分属不同阶段，但都由同一状态定义。
- 重复聚灵词条可以每回合给多层，但仍受 10 层上限约束。

### 10.2 灼烧

定位：持续伤害体系核心。

- `灼烧` 是负面 DOT 状态。
- 叠层表示强度或次数，但每层伤害规则必须统一。

建议规则：

```yaml
status_burn:
  polarity: negative
  tags: [debuff, dot, burn]
  max_stacks: 10
  tick: target_round_end
  damage:
    kind: dot
    base: source_atk * burn_pct_per_stack * stacks
```

设计重点：

- 灼烧伤害走 `DamagePacket(kind=dot, tags=[burn])`。
- 默认不触发命中后，不被护盾抵挡，不吃减伤，但吃韧性。
- 引爆效果消耗灼烧层数并产生 `DamagePacket(kind=burst, tags=[burn])`。

### 10.3 护盾 / 裂铠

定位：防御与反制。

普通护盾可以作为通用资源，也可以用状态表示。若需要“破盾反伤”，推荐用状态。

```yaml
status_liekai:
  polarity: positive
  tags: [buff, shield]
  stacking: independent
  shield_amount: value
  on_shield_broken:
    deal_damage:
      kind: reflect
      amount: broken_amount * backlash_pct
```

设计重点：

- 多件裂铠是多个独立实例，独立破裂、独立反伤。
- 护盾抵扣发生在伤害管线的 `Shield` 阶段。
- 反伤默认不触发新的反伤。

### 10.4 净化

定位：状态交互核心。

净化不是“删列表元素”，而是一个 Action，并产生 `StatusRemoved` / `StatusCleansed` 事件。

```yaml
cleanse:
  target: owner
  select:
    polarity: negative
    cleanseable: true
  count: 1
```

设计重点：

- 被净化的状态、层数、来源都要进入事件 payload。
- 涤世等“净化后追伤”监听 `StatusCleansed`。
- 不可净化状态必须在定义上声明，例如死兆。

### 10.5 涅槃

定位：器灵级规则改变。

涅槃应作为脚本处理器，而不是声明式模板。

触发：`BeforeDeath`

行为：

1. 检查本场是否还有复活次数。
2. 取消本次死亡。
3. 恢复一定百分比最大生命。
4. 施加复活后强化或虚弱。
5. 记录结构化日志。

设计重点：

- 复活优先级高于普通死亡结算。
- 处决是否能被复活拦截必须由 `DamagePacket.can_be_revived` 或 `DeathEvent.death_kind` 明确。
- 同一战斗最多触发次数必须写在效果定义中。

## 11. 数值控制原则

### 11.1 法宝词条定位

法宝词条是多槽位、小颗粒、可构筑效果。

建议：

- 单个词条不要同时提供多个高乘区收益。
- 多数词条应围绕状态、触发条件、局部修正展开。
- 重复词条允许，但必须有总上限或边际递减。
- 词条池应减少“纯 +X% 伤害 / -X% 伤害”的重复项。

### 11.2 器灵神通定位

器灵神通是单体、大颗粒、改变规则的效果。

建议：

- 每个神通最好有鲜明战斗风格。
- 不要只是更大的百分比词条。
- 可以改变事件规则，例如死亡拦截、灼烧引爆、咒印处决、偷取状态。
- 必须有触发频率、次数、阈值或资源约束。

### 11.3 层数与频率

默认建议：

| 类型 | 推荐限制 |
|---|---|
| 攻击成长层 | 5 ~ 10 层 |
| 易伤 / 减疗 | 3 ~ 5 层 |
| DOT | 5 ~ 10 层 |
| 护盾 | 按最大生命或护体比例设上限 |
| 复活 | 1 次，特殊神通可多次但递减 |
| 处决 | 必须有清晰前置标记和回合窗口 |
| 随机负面 | 每回合 / 每行动次数限制 |

### 11.4 PvP / PvE 场景修正

场景标签继续保留，但作为一等条件使用。

常见标签：

- `scene_tower`
- `scene_boss`
- `scene_ladder`
- `scene_pvp`
- `scene_spar`
- `scene_arena`
- `scene_proving_ground`
- `scene_bounty`
- `scene_robbery`

建议：

- 如果某效果在 PvP 中过强，应通过场景修正或效果定义限制，而不是在代码里硬分支。
- 证道战场的临时构筑可以用 `source_type=temporary`，不应特殊侵入核心战斗。

### 11.5 防爆炸组合

建议设置全局软上限：

- 造成伤害提高总量上限。
- 受到伤害提高总量上限。
- 受到伤害降低总量上限。
- 暴击率 / 闪避率上下限。
- 护盾占最大生命比例上限。
- 单回合额外伤害触发次数上限。

这些上限应由战斗配置统一定义，而不是散落在效果实现中。

## 12. 战报设计

### 12.1 战报分层

V2 战报分三层：

1. **机制层 LogEvent**
   - 完整结构化事件，用于测试与调试。

2. **展示层 BattleLine**
   - 面向玩家的中文句子。
   - 可以根据重要度筛选。

3. **兼容层 ActionLog**
   - 如旧 UI 仍需要，可把 BattleLine 转成现有 `ActionLog`。

### 12.2 重要度

建议每条日志有 `importance`：

| importance | 用途 |
|---|---|
| `debug` | 调试用，默认不展示 |
| `minor` | 小层数、小治疗、小状态 |
| `normal` | 普攻、常规伤害 |
| `major` | 暴击、引爆、大额治疗、破盾 |
| `critical` | 复活、处决、胜负关键 |

普通战报展示 `normal+`，完整战报展示 `minor+`，调试战报展示全部。

### 12.3 可解释性

对于关键伤害，调试战报应能展开：

```text
基础伤害 10000
攻方增伤 +30% => 13000
目标易伤 +20% => 15600
目标减伤 25%，穿透 10%，有效减伤 15% => 13260
护盾抵扣 3000 => 10260
境界韧性 12% => 9028
最终造成 9028 点伤害
```

玩家普通战报不必展示所有细节，但系统内部应保留足够信息，方便排查平衡问题。

## 13. 现有内容重做策略

### 13.1 法宝词条筛选方向

现有 47 个词条可以按机制归类，而不是逐个搬迁。

建议保留 / 重做的机制族：

| 机制族 | 代表旧词条 | V2 方向 |
|---|---|---|
| 灵势成长 | 凝神、聚灵 | 合并为稳定成长构筑核心 |
| 灼烧 DOT | 灼魂、焚心、烬火、焚劫、余烬 | 统一 burn 标签、DOT、引爆、余烬收益 |
| 咒系标记 | 咒缚、蔓咒 | 统一 curse / mark 体系 |
| 创伤 / 易伤 | 蚀骨、裂创 | 合并为负面层数体系 |
| 身法节奏 | 掠影、疾锋、风行、幻步、破空 | 做成先手、闪避、行动节奏构筑 |
| 护盾防御 | 镇关、裂铠、藏壁、护元 | 统一 shield 体系，裂铠作为反制分支 |
| 净化驱散 | 净华、清心、噬印 | 统一 cleanse / dispel / steal 体系 |
| 低血反击 | 转机、续命、秽生 | 统一 low_hp 触发规则 |

建议删除或合并：

- 只提供相似百分比增伤 / 减伤、没有构筑意义的重复词条。
- 需要大量特判但玩家难理解的边缘效果。
- 与器灵神通定位冲突的“大颗粒规则改变”词条。

### 13.2 器灵神通筛选方向

器灵神通应保留“改变战斗规则”的感觉。

建议重点保留 / 重做：

| 机制 | 旧神通素材 | V2 方向 |
|---|---|---|
| 复活 | 涅槃 | 死亡拦截 + 复活后变化 |
| 处决 | 绝命 | 咒印 / 死兆 / 斩杀窗口 |
| 灼烧引爆 | 蚀焰、焚脉 | burn 构筑核心神通 |
| 状态偷取 | 窃道、夺锋 | 状态交互型神通 |
| 净化追击 | 涤世 | cleanse 后产生收益 |
| 控制 | 禁脉 | 行动封禁，但频率要严格限制 |
| 充能审判 | 雷罚 | 充能到阈值后爆发 |
| 反击反伤 | 反棘、归锋 | 防御反制流派 |
| 首回合节奏 | 追风、逐影 | 先手 / 首击 / 命中暴击操控 |

建议弱化：

- 纯数值加成型神通。
- 与法宝词条区别不明显的“小概率小收益”神通。
- 随机性强但反馈弱的神通。

## 14. 迁移路线草案

### 阶段 1：设计文档

产出本文，确认：

- 核心抽象。
- 生命周期。
- 伤害矩阵。
- 状态模型。
- 效果编写方式。
- 旧内容筛选方向。

### 阶段 2：最小原型

新增独立 V2 模块，不接入线上命令。

建议路径：

```text
bot/services/combat_v2/
  engine.py
  events.py
  actions.py
  damage.py
  statuses.py
  effects.py
  logs.py
```

最小原型只支持：

- 双方普攻。
- 命中 / 暴击。
- 统一 DamagePacket。
- 状态添加与衰减。
- 结构化日志。
- 2 ~ 3 个样例效果：聚灵、灼烧、护盾。

### 阶段 3：效果样板

把几个代表性机制做成标准模板：

- 叠层成长：聚灵 / 灵势。
- DOT：灼烧。
- 护盾反制：裂铠。
- 净化：净华 / 涤世样板。
- 复活：涅槃脚本样板。

该阶段重点验证：

- 新效果是否真的好写。
- 事件顺序是否清晰。
- 战报是否比旧系统更好解释。

### 阶段 4：内容重做

重新设计 V2 法宝词条池和器灵神通池。

原则：

- 先少量高质量，不急着恢复旧数量。
- 每个机制族至少有 2 ~ 4 个可搭配效果。
- 器灵神通数量可以先少于旧版，但每个要有明显风格。

### 阶段 5：灰度接入

优先接入低风险或独立玩法，例如：

1. 证道战场 V2 测试节点。
2. 内部测试命令。
3. 新赛季 / 新活动战斗。
4. 最后再切换通天塔、论道、擂台等主玩法。

### 阶段 6：旧系统退场

当 V2 内容池、测试覆盖、战报展示稳定后，再考虑：

- `CombatService` 作为兼容 facade 调用 V2。
- 旧 `combat_service.py` 内部逻辑逐步冻结。
- 老词条数据迁移为 V2 效果 ID。
- 删除不再使用的旧私有 helper。

## 15. 验收问题

Combat V2 真正进入实现前，需要能明确回答以下问题：

1. 新增一个普通法宝词条，需要写哪些声明？
2. 新增一个复杂器灵神通，需要写哪个 handler？
3. 一笔伤害是否吃增伤、减伤、护盾、韧性，在哪里声明？
4. 同时触发护盾、反伤、复活、处决时，谁先谁后？
5. 一个状态能否被净化、偷取、转移，在哪里声明？
6. 重复词条如何叠加，在哪里限制上限？
7. 证道战场临时效果如何进入战斗？
8. 战报如何从结构化事件转成玩家可读中文？
9. PvP 中某效果过强时，是改数值、改场景修正，还是改触发频率？
10. 旧内容哪些保留、哪些合并、哪些删除？

只有这些问题有稳定答案后，才应该开始大规模迁移旧战斗内容。
